The epic tier, and a Linear sync you can actually configure

Two changes, one page. Features become the thing anton runs; product epics become the tier above them that stakeholders read. Then a sync panel that publishes exactly the tiers you choose — because the tier you execute is rarely the tier anyone else wants to see.

The three tiers

what each one is for, and who reads it
epic A product outcome. Spans several features, carries one area: label. Read by people who don't read code. Lives in Linear as a top-level issue, indistinguishable from a synced feature — push carries neither hierarchy nor tier.
feature One shippable delivery unit — one worktree, one PR. This is what anton runs. Approved, claimed, run-leased, shipped. What today's beads epic already is.
task · bug · chore The working layer. Executed as part of their feature's run. Engineering only. Never leaves the board.
Migration-free rule

A bead is runnable if it's a feature, or a parentless task/bug, or an epic with no feature children. Today's boards keep running untouched; an epic becomes a container the moment a feature lands under it.

Open

An epic with both feature children and loose task children is legal in bd but ambiguous here. Proposal: those tasks render, aren't independently runnable, and get a lint nudge.

Approval stays per feature. Approving an epic does nothing — approval is a per-PR gate, and one button that launches six PRs is not a gate. Bulk-approve can come later as a convenience, clearly labelled as such.

Why a table

The roadmap is read, not operated. A table answers "what's in flight and where does it live in Linear" in one scan; a second board would only duplicate the first.

Sync legibility

Linear sync

Settings › Automation — you pick the tiers, anton builds the command
Sync to Linear
When it runs

Push-triggered syncs are debounced to one every 5 minutes — a single run writes to a bead dozens of times, and each write nudges a push. The schedule is the backstop for when a push-triggered sync fails.

Direction

Push keeps beads authoritative. Both enables editing in Linear, and needs a conflict rule.

Which tiers sync

The push is flat: every tier you pick lands as a top-level issue, because bd sends no parent. --type only chooses what gets pushed — it does not travel with the issue, so Linear cannot tell an epic from a feature. Grouping is the Linear project the area: routing sets when the issue is created. Anything you leave off stays local.

Also include

Closed beads carry the completion back to Linear. Open-only leaves shipped work showing as in-flight.

The one real control

Everything above is a thin skin over bd linear sync flags. Showing the command as you build it means the panel never becomes a lossy abstraction over the CLI.

Preview before push

Every setting is reversible except a bad first push, which creates issues in someone else's Linear — and except the project each issue was created in, which no later change to the routing table can move. Dry-run is one click and reports counts, not a spinner — but it needs a credential (bd reaches the live API before it previews) and reports one line per bead, so anton derives the counts.

Before the first push

bd writes the Linear ref into external_ref. Any board still carrying legacy gh-<n> PR pointers there loses them. The job must refuse to push until the pr-ref migration has run.

Lease churn

Settled 2026-09-05: push never sends labels, so the run-lease stays a label and nothing moves to metadata. What it costs is API calls — one read per linked bead every push, plus a write for every bead carrying a structured acceptance_criteria, design or notes field. Size it against what per-area routing selects, not the 197 epics+features the tier chips match: on this panel's --state all default that was 122 writes against N=194 on 2026-09-05 if a feature inherits its parent epic's area:, and 10 against N=11 if it does not — an open routing question that swings the budget 18×. Open only moves it again (N=44, 17 writes on the inherited reading). A partial routing table is budgeted from its own areas' rows — the per-area write share runs 18–100% — not by scaling that aggregate. It does not decay — closed beads never leave an Open and closed population and anton keeps writing notes. That is what the debounce caps.

Credentials

Read from the environment, never stored in anton.db — same posture as gh. The panel reports what it found and stops there.
